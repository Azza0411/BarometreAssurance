# Cas particuliers — extraction des KPI "Charge de sinistres" et "Résultat Net"

Trois KPI répartis sur 3 tableaux résumés (pas les annexes par catégorie
déjà traitées dans CAS_PARTICULIERS_ANNEXE12.md / _ANNEXE13.md) :
  - "L'état de résultat technique de l'assurance vie" -> Charge de sinistres Vie
  - "L'état de résultat technique de l'assurance non-vie" -> Charge de sinistres Non-Vie
  - "L'état de résultat arrêté au [date]" -> Résultat Net

## Cas résolus

| Société / document | Problème rencontré | Solution appliquée |
|---|---|---|
| STAR | Code de ligne collé sans espace au libellé (ex: "chnv1charge de sinistres") | Motifs non ancrés en début de chaîne (recherche de sous-chaîne, comme pour les autres tableaux) |
| STAR, COMAR | Le total de "Charges de sinistres" est parfois sur une ligne séparée après les sous-éléments (STAR : ligne non libellée ; COMAR : code répété seul "CHV1") | Balayage vers l'avant borné par le préfixe de code de ligne (ex: "chnv1" englobe "chnv11"/"chnv12" mais pas "chnv2") — même principe que les sections du Bilan |
| GAT | Faute de frappe dans le document source : "sinsitres" au lieu de "sinistres" (lettres transposées) | Motif tolérant les deux orthographes |
| GAT | Titre de page "annexe n 3 etat de resultat technique..." réparti sur plus de lignes que prévu | Fenêtre de lignes vérifiées pour le titre de page augmentée (3 -> 8) |
| COMAR | Tableau Vie sans le mot "technique" dans son titre ("ETAT DE RESULTAT DE L'ASSURANCE VIE") ; ce même titre "sans technique" faisait à tort matcher le résultat GLOBAL (qui exclut seulement les titres contenant "technique"/"catégorie") | Motif de détection du résultat global élargi pour exclure aussi "assurance vie"/"assurance non vie" ; recherche qui continue sur les pages suivantes si la ligne n'est pas trouvée sur la première page correspondant au titre (au lieu d'abandonner) |
| ASTREE | Ligne "Résultat net" nommée "Résultat net après modifications comptables" (sans "de l'exercice") | Motif réduit à la racine commune "resultat net" |
| BH | Titre de page avec texte inséré entre "assurance" et "vie/non-vie" ("assurance et/ou de la réassurance non Vie") | Motif de titre capturant le texte intermédiaire, puis vérification de la présence de "non" dans ce texte capturé plutôt qu'un enchaînement direct exigé |
| BH | Code de ligne avec espace ("CHNV 2" au lieu de "CHNV2" chez GAT/COMAR) | Motif de détection de code tolérant l'espace optionnel |

| LLOYD_TUNISIEN, LLOYD_VIE, MAGHREBIA, MAGHREBIA_VIE, TUNIS_RE (2017-2025 selon société) | Découvert le 2026-08-06 (audit Vue par Assurance, année 2024) : "Charge de sinistres Vie/Non-Vie" introuvable malgré Ratio combiné/frais présents. `TECH_TITLE_PREFIX_RE` (titre de page) exigeait "resultat [technique] de l'assurance <...> vie" — 5 formulations différentes y échappaient : LLOYD_TUNISIEN utilise le format "Annexe 3/4 État de résultat [non] vie" (sans "de l'assurance") ; LLOYD_VIE écrit "résultat technique **vie** de Lloyd Vie" (vie avant "de la compagnie", pas après "de l'assurance") ; MAGHREBIA insère "et de la réassurance" entre "assurance" et "vie", au-delà de la fenêtre de 40 caractères ; MAGHREBIA_VIE (société mono-branche) ne mentionne "vie" nulle part dans son titre ; TUNIS_RE écrit "résultat technique **-** vie" (tiret, sans "de l'assurance"). | **Fixé** en abandonnant le titre de page comme signal PRINCIPAL de désambiguïsation Vie/Non-Vie, au profit du CODE DE LIGNE (CHV1 = Vie, CHNV1 = Non-Vie — code standard CMF, présent et fiable dans les 5 cas). Le titre de page reste un REPLI pour les rares lignes sans code (ex: GAT_VIE : "charge de sinistres note", sans "chv1" glué). Validé par comparaison ancien/nouveau code sur les 223 documents CMF : 43 changements, tous `None → valeur` (aucune régression, aucune valeur correcte invalidée). Voir `_find_sinistres_value` dans `resultat_kpi_extractor.py`. |

| ATTIJARI (2015, 2017, 2019) | Découvert le 2026-08-18 (retour utilisateur sur ROA/ROE 0% affichés à tort) : le document a DEUX lignes matchant "resultat net" sur la même page — "Résultat net de l'exercice" (sous-total intermédiaire, littéralement à 0 dans ces 3 PDF) puis "...après modifications comptables" juste en dessous (la vraie valeur finale). `_find_first_column_value` retournait la première ligne trouvée, donc systématiquement ce faux zéro. | **Fixé (généralisé, pas propre à ATTIJARI).** Une ligne contenant "après modifications comptables" est désormais toujours préférée si elle existe sur la page ; repli sur la première ligne plausible sinon (comportement inchangé pour les documents n'ayant que la forme simple). Résultat Net ATTIJARI : 2015 0→1 395 895, 2017 0→3 812 863, 2019 0→6 019 911. |
| ZITOUNA_TAKAFUL (2025) | Découvert le 2026-08-18 (même retour utilisateur, ROA/ROE 0% affichés à tort) : le "R" de "Résultat" se retrouve séparé du reste du mot par un espace parasite ("r esultat net de l'exercice") sur la vraie ligne de l'État de résultat — la regex stricte ne la matchait donc jamais, et l'extraction retombait sur `RESULTAT_EXERCICE_FALLBACK_RE`, qui matche AUSSI (même libellé exact) une ligne d'un tableau différent (variation des capitaux propres) dont la 1ère colonne n'est pas le bon résultat → "Résultat Net" extrait à 0 (au lieu de 7 379 895, vérifié cohérent avec 2024 = 8 540 196). | **Fixé (généralisé).** `RESULTAT_NET_RE`/`RESULTAT_EXERCICE_FALLBACK_RE` (dans `resultat_kpi_extractor.py` ET `takaful_kpi_extractor.py`, qui a sa propre copie) tolèrent désormais un espace optionnel après le "r" (`r\s?esultat`) — artefact de rendu PDF pouvant en théorie toucher d'autres documents, pas une regex ad hoc pour Zitouna. |

| LLOYD_TUNISIEN, MAGHREBIA, MAGHREBIA_VIE, TUNIS_RE — page PDF affichée par `/kpi-detail` pour "Charges de sinistres Vie/Non-Vie" | Découvert le 2026-08-18 en corrigeant l'affichage de la page source (`api/services/pdf_sections.py::_find_sinistres_page`, nouvelle fonction miroir de `_find_sinistres_value` mais renvoyant la page plutôt que la valeur) : sur les 17 sociétés conventionnelles ayant cette donnée en base, 13 s'affichent désormais correctement (voir cas résolus), mais ces 4-là échouent encore ("page introuvable") — précisément les 4 sociétés déjà nommées dans la docstring de `_find_sinistres_value` comme n'ayant AUCUN code de ligne CHV/CHNV détectable sur cette ligne précise, forçant un repli sur le titre de page (fragile, 5 formulations différentes documentées). | Non corrigé — même limitation que l'extraction de la valeur elle-même (le correctif page-only hérite fidèlement de la même fragilité de détection par titre, sans la corriger). Nécessiterait de retravailler le repli par titre de `_find_sinistres_value`/`_find_sinistres_page` pour ces 4 formulations précises. |

## Cas non résolus (à reprendre plus tard)

| Société / document | Problème | Piste envisageable |
|---|---|---|
| BH | KPI "Charge de sinistres Non-Vie" incorrect : quand le code de la section suivante a un chiffre séparé par un espace ("CHNV 2"), ce chiffre est absorbé comme donnée numérique par l'extracteur de nombres plutôt que reconnu comme faisant partie d'un code de ligne — ceci casse à la fois la détection de la frontière de section ET le comptage de colonnes de la ligne concernée | Reconstruire les codes de ligne au niveau des mots bruts (avant filtrage numérique/texte) plutôt qu'après coup sur le libellé déjà séparé des nombres — chantier plus large touchant potentiellement bilan_kpi_extractor et annexe12/13_kpi_extractor aussi |
| STAR | KPI "Charge de sinistres Vie" introuvable (page correspondante scannée en image pour ce document) | OCR |
| GAT | Valeurs "Charge de sinistres" (Vie et Non-Vie) non vérifiées indépendamment (seulement 2 colonnes trouvées sur la ligne d'en-tête au lieu des 4 attendues — possible fusion de chiffres à valider) | Vérifier manuellement contre le PDF source |
| **TUNIS_RE (2024 spécifiquement, années antérieures non affectées)** | Découvert le 2026-08-06 : "Charge de sinistres Vie/Non-Vie" ET le Bilan ("Total actif"=2, "Résultat Net"=2, "Placements"=8 — des fragments, pas de vraies valeurs) restent introuvables même après le fix ci-dessus. Cause RACINE identifiée précisément : TUNIS_RE 2024 utilise un séparateur de milliers en POINTS ("8.671.061" pour 8 671 061), et le PDF **scinde ce nombre en deux mots distincts** ("8" et ".671.061") — vérifié via `page.extract_words()`. Le second fragment (commence par ".") ne correspond à aucun format numérique reconnu par `NUMERIC_TOKEN_RE` (`bilan_kpi_extractor.py`, qui suppose un séparateur de milliers = ESPACE) et est silencieusement rejeté ; seul le chiffre isolé ("8", "2", "4"...) survit, d'où les valeurs absurdement petites observées partout où ce format apparaît. | **Non corrigé** — nécessite un nouveau pas de "recollage" de mots scindés dans `_extract_numeric_clusters`/`NUMERIC_TOKEN_RE` (même famille que `_split_glued_negative`/`_split_glued_close_paren`, déjà utilisés pour des artefacts de découpage PDF similaires), mais cette fonction est partagée par TOUS les extracteurs (Bilan, Annexe 12/13, Résultat...) — portée bien plus large qu'un correctif localisé à une société, à valider avec l'utilisateur avant implémentation (voir échange du 2026-08-06). |
